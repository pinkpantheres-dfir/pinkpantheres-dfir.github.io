Maze of Traffic

Uncovering DNS-Based Data Exfiltration Through Network Forensics. The investigation moved from tempting HTTP activity to anomalous DNS patterns, then to payload reconstruction—revealing stolen files, system reconnaissance artifacts, and how DNS tunneling blended into normal infrastructure noise.

#forensics #dns #dfc2024 #networkforensics #incidentresponse

Summary

A suspected data breach started the investigation. The goal was straightforward: determine how data left the environment, identify what was stolen, and understand the attacker’s methodology.

The attacker didn’t need “loud” protocols—DNS was enough.

The key outcome: sensitive data exfiltration occurred via DNS tunneling, using unusually encoded, long subdomains to smuggle content through what looked like routine DNS traffic.

Initial Observations

After validating the evidence image and extracting network logs, the first view showed many HTTP POST requests. Because exfiltration is often associated with web traffic, HTTP became an initial focus.

But the more carefully the requests were reviewed, the less suspicious they looked. There were no obvious signs of large-scale transfer or attacker-controlled destinations.

Investigator’s Note:
One of the easiest mistakes in an investigation is becoming attached to the first theory. When the evidence didn’t support HTTP exfiltration, focus was deliberately shifted rather than forced to fit a hypothesis.

Following the DNS Trail

DNS is frequently treated as background noise. It’s essential infrastructure, widely used, and often inspected less than web traffic. Attackers know this—and frequently abuse DNS as a covert communication channel.

To test the DNS hypothesis, DNS activity was filtered from the Zeek logs and sorted chronologically.

DNS Filtering (Zeek Query)
proto=="udp"
and qtype_name!="AAAA"
and this["id.resp_h"]=="8.8.8.8"
| fuse
| sort query
| sort ts

Turning Point:
Long encoded subdomains appeared almost immediately—behavior that is rarely normal in legitimate DNS usage. That anomaly strongly indicated DNS tunneling.

Building the Hypothesis

The working theory was that the attacker:

  • fragmented sensitive data,
  • encoded it,
  • embedded fragments into DNS subdomains,
  • and relied on 8.8.8.8 as a public resolver to forward queries toward an attacker-controlled authoritative server.

If the fragments could be reconstructed correctly, the stolen content should reappear.

Reconstructing the Payload

DNS records were exported to JSON and scripts were used to rebuild the encoded content. The approach parsed query strings, isolated the payload fragments, and reassembled the original data.

Payload Extraction/Reconstruction (Python)
import json

log_file = open("dns-data").read()
data = json.loads(log_file)

for obj in data:
    print(obj['query'])

Reconstruction revealed filesystem information, user account details, and references to confidential project documents.

What Was Actually Stolen?

The primary target appeared to be a confidential PDF at: 

/mnt/volume/project/confidential/Confidential_Document.pdf

Additional leaked information included contents of the Linux passwd file, directory structures, and other system reconnaissance data.

Recovered MD5:
bd871b58d122275c4d0a84b76799e665

Why DNS Tunneling Works

DNS tunneling remains effective because DNS is essential infrastructure. Many organizations carefully inspect web traffic but pay significantly less attention to DNS. As a result, attackers can exfiltrate information while generating DNS queries that “look normal” at a superficial glance.

In this case, the public resolver acted only as an intermediary: it forwarded the queries without interpreting the meaning of the encoded subdomains.

Defensive Recommendations

  • Monitor DNS query logs continuously.
  • Alert on excessively long subdomains.
  • Restrict outbound DNS to approved resolvers.
  • Deploy Zeek, Suricata, or similar IDS solutions.
  • Implement DLP controls.
  • Perform regular threat-hunting exercises.

Lessons Learned

This investigation reinforced an important principle: data exfiltration doesn’t always rely on obvious protocols like HTTP or FTP. Even a fundamental service like DNS can become a covert communication channel when monitoring is insufficient.

It also highlighted the value of challenging assumptions. The most visible traffic was a distraction—while the real attack lived inside routine DNS activity.

Conclusion

By analyzing Zeek logs, identifying anomalous DNS behavior, and reconstructing encoded payloads, the exfiltration method was determined, the stolen data was identified, and the attacker’s DNS tunneling approach was understood.
