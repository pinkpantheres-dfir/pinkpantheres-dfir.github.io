When the Header Holds the Truth

A DVR vendor hides decoding parameters inside a proprietary viewer rather than the file itself. A filesystem wipe means the viewer can't help. What's left is raw bitstream and if you know how to read it, the resolution is hiding in the first 15 bytes.

Executive Summary

DVR manufacturers deliberately strip H.264 decoding parameters from stored footage and embed them inside proprietary viewer software instead a form of DRM by obscurity. When filesystem-level directory entries are deleted or corrupted, the viewer can't locate the file and the footage appears unrecoverable. This challenge required extracting the resolution from a raw H.264 SPS NAL unit, then using a creative reference-profile technique to reconstruct and actually play back the video.

What made this one interesting was the two-layer problem. On the surface it looks like a video analysis task. But underneath, it's a trust-the-spec exercise you have to go back to the ITU-T H.264 specification, understand how SPS NAL units encode width and height as Exp-Golomb coded fields, and work through the bit arithmetic manually to get a number the broken file refuses to tell you directly.

The answers were 1280×720 for the resolution, and "The Sun by Edvard Munch" for the recorded masterpiece derived by using a reference video profile from a parallel challenge to unlock the broken footage in fix.video.

Two NAL units. The first starts at offset 0x00 with the 4-byte start code 00 00 00 01, and the NAL header byte is 0x67. The second starts at 0x10 with start code 00 00 01 and header byte 0x68. I'll come back to what those mean in a moment but the structure is already telling me something clean: this is a legitimate H.264 header fragment, properly formed.

Step 3 Decoding the NAL Unit Headers

The 8-bit NAL unit header has three fields: a forbidden zero bit, a 2-bit nal_ref_idc, and a 5-bit nal_unit_type. Mapping 0x67 to binary:

0forbidden zero
1nal_ref_idc
1nal_ref_idc
0nal_unit_type
0nal_unit_type
1nal_unit_type
1nal_unit_type
1nal_unit_type

0x67 = 01100111. Forbidden zero: 0. nal_ref_idc: 11 (3 referenced). nal_unit_type: 00111 = 7 = SPS. And 0x68 decodes the same way to nal_unit_type = 8 = PPS. So we have exactly what we need: a Sequence Parameter Set followed by a Picture Parameter Set. The resolution lives in the SPS.

Why This Matters

DVR manufacturers strip these NAL units from the stored .264 data and embed them inside the viewer DLL. Without the SPS, a decoder has no way to know the frame dimensions, chroma format, or reference frame count the video is unplayable. This .hed file is effectively the stolen key. My job is to read it.

The two values that matter are pic_width_in_mbs_minus1 and pic_height_in_map_units_minus1. These are Exp-Golomb coded fields embedded in the bitstream. I'll walk through the arithmetic below.

Note on Profile IDC

The challenge description notes that the DLL-based decoding parameters don't match a "predefined profile." In the SPS, profile_idc = 100 maps cleanly to High Profile but some older DVR implementations use non-standard profile signalling. The resolution arithmetic is independent of this and can be derived from the width/height fields alone.

Step 5 Deriving Width and Height

H.264 encodes frame dimensions in units of macroblocks (16×16 pixel blocks), not raw pixels. The decode formula from the spec is: 

Width  = (pic_width_in_mbs_minus1 + 1) × 16
Height = (pic_height_in_map_units_minus1 + 1) × 16 × (frame_mbs_only_flag ? 1 : 2)

Here's the step-by-step for both dimensions. The Exp-Golomb decode for width works through the byte 0x02 0x80:

Width Calculation
Bytes in bitstream: 0x02 0x80 → binary: 00000010 10000000
Exp-Golomb leading zeros: 6 → code prefix gives offset (1 << 6) − 1 = 63
Next 6 info bits: 010000 = 16 → value = 63 + 16 = 79 (0x4F)
pic_width_in_mbs_minus1 = 79
Width = (79 + 1) × 16 = 1280 px
Height Calculation
Byte in bitstream: 0x2D → binary: 00101101
Exp-Golomb leading zeros: 5 → code prefix gives offset (1 << 5) − 1 = 31
Next 5 info bits: 01101 = 13 → value = 31 + 13 = 44 (0x2C)
pic_height_in_map_units_minus1 = 44
frame_mbs_only_flag = 1 (progressive, not interlaced)
Height = (44 + 1) × 16 × 1 = 720 px

No crop offsets, so no adjustment needed. The full luma dimensions from the SPS are exactly what I calculated:

Q2: Decoding the Video and Identifying the Masterpiece

Step 6 The Problem with Raw .264 Files

Having confirmed the header, I turned to Problem_Frame_Data.264. The DVR's proprietary handling means the frame data is stored without embedded decoding parameters those live in the DLL, not the file. So even with the SPS in hand, standard decoders like VLC or ffmpeg choke on it. There's no container, no SPS/PPS in the bitstream, and no profile reference. It's raw, undecoded frame data that needs an external parameter set to make sense of it.

The manual-documented resolution (1920×1080) also doesn't match the actual SPS which means feeding the file to a decoder using the "expected" dimensions would produce garbage output even if it ran at all.

Step 7 Using fix.video as a Reconstruction Tool

I found fix.video, which is built specifically for broken or incomplete video files. It can take a damaged file and repair it if it can infer a valid codec profile or, more usefully, it accepts a separate reference video file whose codec parameters are used as the profile source for the broken footage.

Uploading Problem_Frame_Data.264 alone produced no valid profiles the tool correctly identified that the file lacked embedded parameters and couldn't self-repair.

The Insight That Unlocked This

I was simultaneously working through challenge 251 "Time is a Masterpiece" which involved recovering an mp4 from a DVR binary file. Once I had that mp4 extracted, it occurred to me: both challenges involve DVR footage. If they're from the same DVR device, the codec profile in the 251 mp4 would be compatible with the 204 frame data. I uploaded the 251 mp4 as the reference profile in fix.video and the preview appeared.

Step 8 Preview and Identification

With the 251 mp4 as the reference, fix.video successfully reconstructed and previewed Problem_Frame_Data.264. The repaired output was delivered as a QuickTime/MOV container at 1920×1080, h264 (Main), 25 FPS, 2.2 Mb/s the full video information confirmed a clean repair.

The preview showed a CRT monitor displaying a colorful, radiant painting with dramatic light emanating from a central point. The image was unmistakable a piece I'd encountered in art history contexts. The composition, the explosive solar motif, the style: this was Edvard Munch's "The Sun."

What This Challenge Is Actually About

On the surface, 204 is a video forensics problem. But the deeper lesson is about what DVR manufacturers are doing when they "apply security" to footage: they're not encrypting it, they're just hiding the decoder key in proprietary software. The moment that software is unavailable because it was deleted, or the filesystem was wiped, or the dedicated viewer just won't load a file without a directory entry the footage appears inaccessible.

It isn't. The frame data is intact. The SPS is intact (in the .hed file). The only missing piece is the bridge between them, and that bridge is reconstructible from the spec and a compatible reference profile.

Forensic Implication

If you're ever handed "unplayable" DVR footage without the proprietary viewer, don't assume the evidence is gone. Look for a .hed or similar extracted header file. Parse the SPS NAL unit directly. Then find any other footage from the same device model in court records, parallel cases, or even manufacturer demo footage and use it as the reference profile for reconstruction. The bitstream itself is almost always intact.

The cross-challenge insight that the 251 mp4 would serve as a compatible profile for 204 came from thinking about the problem at the device level rather than the file level. Both challenges involved the same DVR ecosystem. That was the key.

Forensic Takeaways

  • DVR "security by obscurity" doesn't survive spec-level analysis. Stripping SPS/PPS from stored H.264 data and hiding them in a viewer DLL is not encryption. A forensic examiner who knows the NAL unit structure can extract resolution, profile, level, chroma format, and reference frame count directly from the embedded header file no proprietary software needed.
  • The Exp-Golomb coding of resolution is a well-documented ITU-T standard. pic_width_in_mbs_minus1 and pic_height_in_map_units_minus1 are in every SPS. If you can extract the SPS payload, you can derive the exact frame dimensions with pen-and-paper arithmetic.
  • Cross-case awareness creates recovery opportunities. Treating parallel cases as isolated silos would have meant failing Q2. Recognising that two challenges shared a DVR ecosystem and that the codec profile from one case could unlock the other is the kind of lateral thinking that separates a comprehensive investigation from a narrow one.
  • fix.video's reference profile feature is a legitimate forensic tool. It's designed for exactly this scenario: frame data without embedded parameters. The critical input is finding a geometrically and codec-compatible reference video. Once that's in place, reconstruction is automated.
  • Manufacturer documentation should be treated as a claim, not a fact. The manual stated 1920×1080. The SPS said 1280×720. In a real case, using the documented resolution to decode footage without verifying against the actual SPS would produce distorted evidence. Always verify against the bitstream.

Conclusion

The 204 challenge is a clean demonstration of why proprietary DVR "security" is forensically transparent to anyone willing to read the H.264 specification. The resolution 1280×720 was encoded in 15 bytes of SPS payload, accessible to any examiner with a hex editor and a basic understanding of Exp-Golomb variable length coding. The frame data was recoverable once I had a compatible reference profile from a parallel case.

The painting on the screen was "The Sun" by Edvard Munch an apt image, as it turns out, for a challenge about looking past an obscuring layer and finding what's actually there.

Closing Note

DVR footage is involved in a significant proportion of real-world criminal cases assault, theft, homicide. The pattern of "inaccessible" footage due to proprietary viewer requirements is far more common than it should be. If the bitstream exists, the footage is recoverable. The spec is public. The tools exist. Don't accept "unplayable" as a final answer.
