Windows Lateral Movement — Every Move Logged

The attacker created two accounts, stole a hash, installed a malicious service, used Impacket's smbexec.py, then walked straight in through RDP. They thought they were being methodical. But they did all of it on a system that was logging everything — and they left a 26-hour trail from first account creation to final logoff.

What We're Looking At

The challenge brief describes a realistic corporate attack scenario: monitoring or security solution accounts are often added to administrator groups for convenience. Companies register them with the same password everywhere. An attacker who gets hold of those credentials — or just their hash — can move laterally across an entire environment without ever breaking encryption.

The task: analyze the VHDX image of a compromised Windows system, identify every timestamp where the attacker accessed the machine, and determine exactly which lateral movement methods and tools were used during each access. Timestamps needed to be UTC, exact to the second.

This is purely an event log forensics challenge. No malware reversing, no network captures. Just Windows Security logs, System logs, and the attacker's mistakes preserved in them.

Starting Point: Hash Verification and Evidence Extraction

Before I touch anything, I verify the hash. This is a discipline I don't skip — not because I think the evidence has been tampered with, but because if I ever need to defend this work, I need to prove chain of custody from the first step. 

md5sum 102_target.vhdx
0cb76ba40ee240fcd236c752aaad9e07  102_target.vhdx

Hash matched. I mounted the VHDX in FTK Imager and extracted the event logs from C:\Windows\System32\winevt\Logs\ — specifically Security.evtx, System.evtx, Microsoft-Windows-TerminalServices-*.evtx, and the WMI operational log. Then I ran Chainsaw across the full set and also went through them manually with EvtxEcmd output.

The reason I use both: Chainsaw is fast and catches known-bad patterns immediately, but it can miss things if the activity doesn't match a Sigma rule. Manual review of the EvtxEcmd CSV catches the gaps. Between the two, I'm confident I have the full picture.

Phase 1 — Pre-Lateral Movement: Account Setup

Day 1: A Foothold Planted

The earliest malicious activity in the logs is on 2024-05-18. The attacker creates a user account called dean on DESKTOP-D3EB1AE at 08:24:30 UTC. Within one second — literally one second later — there's an explicit credentials logon attempt using that same account (Event 4648). At 08:25:07 they log in locally as dean (Logon Type 2) from a machine called WIN-4QC6J2CTQTS.

// why this matters

Creating a user and immediately attempting to log in with explicit credentials within one second is not human behavior — it's scripted. This tells me the attacker wasn't manually typing at a keyboard. They had tooling that automated the account creation and first-use verification. That's a different threat profile than someone bumbling around manually.

The same evening on WIN-4QC6J2CTQTS, two more accounts appear: WDAGUtilityAccount at 23:41:23 and defaultuser0 at 23:43:24. The defaultuser0 account is immediately added to the Administrators group (Event 4732). This is the attacker building out their administrative presence across the environment — not just one machine, multiple systems.

Day 2: The Real Account and Privilege Escalation

The next morning, 2024-05-19 at 11:10:32, the attacker creates a second account on DESKTOP-D3EB1AE: secadmin. The name is deliberately chosen to blend in. In most corporate environments, a user called "secadmin" gets ignored — it sounds like a legitimate security administration account.

Simultaneously, they try to reset the password for the dean account (Event 4724). This is persistence management — they're making sure their original foothold account can't be locked out from under them.

Seven seconds later at 11:10:39: secadmin is added to the local Administrators group (Event 4732). Then at 11:12:13: local logon as secadmin (Logon Type 2). And right alongside that logon — Event 4797 fires, showing an attempt to query whether secadmin has a blank password, initiated by user dean. That's the attacker using their first account to probe the second one.

At 11:13:13, Event 4798: secadmin enumerates the local group membership of the dean account. They're checking their own work — making sure the accounts have the access they expect before they start moving laterally.

// the pattern I'm seeing

This is methodical pre-attack staging. Create account → escalate → verify → create second account → verify again → enumerate. Every step confirms the previous one worked before moving forward. It's operationally patient in a way that suggests either a practiced attacker or a playbook they're following.

Phase 2 — Lateral Movement: Three Methods, 25 Minutes

From 11:39 to 12:04 UTC on 2024-05-19 — 25 minutes — the attacker uses three distinct lateral movement methods in sequence. This is the part I found genuinely interesting to reconstruct, because each method leaves different evidence in different log sources.

Method 1: Pass-the-Hash (11:39:09)

At 11:39:09 UTC, Event 4624 fires: a network logon (Logon Type 3) for secadmin from IP 192.168.40.134. The logon process is NtlmSsp. No Kerberos. Source IP is not the local machine.

This is the Pass-the-Hash signature. Pass-the-Hash works by using an NTLM credential hash directly instead of the plaintext password — and NTLM is the giveaway. Modern Windows environments that enforce Kerberos won't show NtlmSsp as the logon process for legitimate remote authentication. Seeing it here, from an external IP, with a freshly created admin account, tells me the attacker captured the NTLM hash for secadmin and used it to authenticate without ever knowing — or needing — the actual password.

// the thing that clicked for me

The attacker created the secadmin account themselves — so they already know the password. Why use Pass-the-Hash at all? Because the tooling they're running (likely something from Impacket or a similar framework) defaults to hash-based NTLM auth for network logons. They didn't switch methods manually. The tool chose NtlmSsp. That tells me more about the attacker's toolkit than just the protocol — they're using a framework that handles everything automatically.

Method 2: Impacket smbexec.py Service (11:39:09 and 11:56:57)

At the exact same timestamp as the Pass-the-Hash logon — 11:39:09 — System Event 7045 fires: a new service named uuLG is installed at %systemroot%\dEtwCyox.exe. The service name is random-looking. The executable has an obfuscated name. This is a malicious service dropped to establish persistence and enable remote command execution.

Then at 11:56:57, another 7045 — this time a service called ssdpxvtN. The naming pattern here is the Impacket smbexec.py signature. smbexec.py works by creating a temporary service with a randomly generated name, using it to execute a command, then deleting the service. The fact that the service name is random and the creation is tied to a network logon over SMB is the fingerprint. 

# What smbexec.py does under the hood:
# 1. Authenticates via SMB using stolen credentials
# 2. Creates a service with a random name via the SCM (Service Control Manager)
# 3. Executes attacker commands through that service
# 4. Service removal happens after execution
# → Event ID 7045 is the paper trail it leaves

I confirmed this by correlating the 7045 events with the network logon records. Same source IP. Same user. Sequential timing. The attacker used Pass-the-Hash to authenticate via SMB, then smbexec.py to run commands remotely on the box — all within the same logon context.

Method 3: RDP (12:04:36 — 12:05:36)

At 12:04:36 UTC, RdpCoreTS Event 131 fires: the RDP server on DESKTOP-D3EB1AE accepted a new TCP connection from 192.168.40.134:53552. One second later at 12:04:37, TerminalServices-LocalSessionManager Event 1149 confirms the user authentication succeeded for secadmin connecting from 192.168.40.134.

At 12:04:38: Security Event 4648 (explicit credentials logon) and Event 4624 with Logon Type 10 — that's the RDP logon type. The attacker now has a full graphical desktop session on DESKTOP-D3EB1AE.

// something I noticed

The attacker used three different methods — PtH, smbexec, RDP — against the same machine in 25 minutes. PtH for initial access. smbexec for remote code execution without a GUI. Then RDP for interactive access. That progression makes sense: they used the command-line tools first to stage whatever they needed, then opened RDP to interact with the system directly. The shift from blind remote execution to interactive GUI access usually means they're about to do something that needs a visual interface — or they want to see the state of the machine themselves.

Phase 3 — Post-Lateral Movement: What They Did Once Inside

The RDP session was brief — under two minutes of active interaction before logoff. But the log entries from inside the session tell a story.

At 12:04:43, a WMI Event 5858 fires: a query targeting Root\Rsop\User attempting to delete an instance. This is likely automated tooling — something running on RDP connection that probes user policy settings. At 12:04:44, TS-LSM Event 21 confirms the RDP session logon succeeded and the file explorer shell started. The attacker has a desktop.

At 12:05:07, Security Event 5379: Credential Manager credentials were read by secadmin. This is credential theft — they're pulling whatever passwords or tokens are stored in Windows Credential Manager on this machine. Those credentials would give them lateral movement vectors to additional systems without needing to repeat the whole attack chain.

At 12:05:36, Event 4634 (logoff) and TS-LSM 40 (RDP session disconnected). At 12:06:13, Event 4647 (user-initiated logoff by secadmin). Then at 12:06:36, System Event 1074: user dean initiates a system restart.

// why trigger a restart

This is the part that made me pause. The attacker used dean — their original foothold account, not secadmin — to restart the machine. A restart clears active connections, flushes some volatile artifacts, and can disrupt monitoring tools or logging agents that don't survive reboots cleanly. It's a light anti-forensic step. Not sophisticated, but deliberate. They didn't log off and walk away quietly — they used dean to pull the rug on whatever was running.

What This Investigation Reinforced

Windows event logs, when you have the right log sources enabled, tell a remarkably complete story. The challenge scenario — stolen credentials used for lateral movement — is one of the most common attack patterns in real incident response. And yet it's almost entirely visible in the logs if you know where to look.

The three things I'd take from this analysis:

  • Event 7045 is underrated. Most people focus on 4624 and 4648 for lateral movement detection. But 7045 — service installation — is often the cleaner indicator of tools like smbexec.py and psexec. The service name randomization that Impacket uses is itself a detectable pattern.
  • NtlmSsp as a logon process on a modern network is a red flag. Kerberos should be handling legitimate remote auth. When you see NtlmSsp in 4624 events for network logons, especially from external IPs, that's Pass-the-Hash territory until proven otherwise.
  • The attacker's operational security was inconsistent. They automated account creation (scripted, one-second timing), used a naming convention that blends in (secadmin), and triggered a restart to clean up volatile state — but they also left a full 26-hour trail of Event IDs and didn't clear the Security log before leaving. Good tradecraft in some areas, sloppy in others. That inconsistency is itself a pattern worth noting when profiling an attacker.
They used three different lateral movement methods in 25 minutes. Every single one left a different evidence type in a different log source. That's what makes this a good forensics challenge — and a realistic one.
