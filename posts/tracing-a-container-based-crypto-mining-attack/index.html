DFIR Research / Digital Forensics Challenge 2024

Cloud Investigation

Investigating a Compromised AWS Workload and a Cryptomining Campaign

#cloud-forensics #aws #docker #incident-response #dfc2024

Challenge Overview

A developer reported that a production server had suddenly become extremely slow. The task sounded simple at first: determine what happened and identify the root cause. However, as I dug deeper into the AWS logs, Docker artifacts, and container records, the investigation evolved into a full cloud compromise case involving exposed services, malicious containers, and cryptocurrency mining malware.

Key Finding: An exposed Docker API allowed attackers to gain control of the host, deploy a malicious container, and install a cryptominer that consumed server resources.

Starting the Investigation

The evidence provided consisted of AWS event logs, Docker records, and container artifacts. My first objective was to understand the environment before looking for signs of compromise.

Cloud investigations are often easier when you first establish a baseline: Who deployed the infrastructure? What was deployed? When was it created? Only after answering those questions does attacker activity begin to stand out.

Identifying the Developer

While reviewing CloudTrail logs, I focused on the userIdentity section. One ARN repeatedly appeared throughout the deployment events: 

arn:aws:iam::058264168288:user/James

This immediately identified the developer account responsible for provisioning the environment.

Investigator's Note
CloudTrail is often the most valuable artifact in AWS investigations because it provides a detailed timeline of actions performed by users, services, and attackers.

Reconstructing the Infrastructure

The deployment records revealed a fairly standard AWS environment located in the Asia Pacific (Seoul) region.

  • Region: ap-northeast-2
  • Instance Type: t3.xlarge
  • AMI: ami-01ed8ade75d4eee2f
  • Private IP: 172.31.57.59
  • SSH Key Pair: master-key.pem

Looking up the AMI identifier revealed that the developer deployed: 

Ubuntu-jammy-22.04-amd64-server-20240411

The initial EC2 creation event occurred on: 

2024-06-30 09:55:38 UTC

Following the Attacker's Trail

Once I understood the legitimate environment, I shifted my attention toward signs of abuse. The biggest clue came from Docker logs.

A warning message repeatedly appeared indicating that the Docker daemon was listening on: 

http://0.0.0.0:2375

This immediately raised concerns because port 2375 exposes the Docker Remote API without encryption or authentication.

Turning Point
Exposing Docker on port 2375 is effectively equivalent to granting root-level control of the host. At this point, I suspected the slowdown was not a performance issue but an active compromise.

Root Cause Analysis

The investigation ultimately identified two critical security weaknesses:

  • Docker Remote API exposed on port 2375.
  • Security group allowed access from 0.0.0.0/0.

Together, these misconfigurations allowed attackers to remotely interact with the Docker daemon, create containers, execute commands, and take control of the environment.

Discovering the Malware

Container logs revealed unusual behavior consistent with cryptocurrency mining. The compromised container was consuming resources and attempting to download additional components from an external repository.

During analysis, I discovered that the image being used was not the legitimate Jenkins image. Instead, it referenced a suspicious repository masquerading as Jenkins. 

https://hub.docker.com/r/jenskin/jenkins

This typo-squatted repository was being used to distribute malware.

Tracking the Infrastructure

Further review of the logs revealed repeated connection attempts to: 

15.164.190.114

This system functioned as the attacker's proxy infrastructure and hosted additional scripts used during the compromise.

Attacker Infrastructure
Proxy Server IP: 15.164.190.114

Malware Identification

After tracing the downloaded payloads and reviewing container activity, the malware sample was identified and its SHA-256 hash recovered. 

c8c111fd4c2b9807d3a9c6f0102c1e8f7d7b8cdb7840a23e9004460a75a99601

The behavior strongly indicated a cryptomining campaign whose primary objective was resource hijacking rather than data theft.

Why the Server Became Slow

The developer initially reported performance degradation. That symptom was ultimately explained by the cryptominer consuming CPU resources, memory, and network bandwidth.

Instead of serving application traffic, the compromised infrastructure was being used to generate cryptocurrency for the attacker.

Defensive Recommendations

  • Never expose Docker API publicly.
  • Require TLS authentication for remote Docker management.
  • Restrict security groups using least privilege.
  • Enable AWS GuardDuty and CloudTrail monitoring.
  • Use container image allowlists.
  • Continuously monitor for cryptomining indicators.
  • Enable MFA for privileged AWS accounts.

Lessons Learned

This investigation highlights how a single cloud misconfiguration can rapidly escalate into full infrastructure compromise.

The attacker did not exploit a sophisticated zero-day vulnerability. Instead, they leveraged an exposed administrative service that should never have been reachable from the public internet.

In cloud security, visibility and configuration management are often just as important as vulnerability management.

Conclusion

By correlating AWS logs, Docker artifacts, and container activity, I reconstructed the attack chain, identified the exposed service responsible for the compromise, traced the malicious infrastructure, and confirmed the deployment of cryptomining malware.

What initially appeared to be a simple performance issue ultimately turned out to be a cloud security incident driven by a preventable configuration weakness.
