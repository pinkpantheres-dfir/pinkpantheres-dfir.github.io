Mem, Oops: Following a Rootkit Through Memory

A Linux memory image. An unsigned kernel module. A process that looked ordinary at first glance. What began as a routine memory triage quickly turned into a layered investigation involving a Diamorphine-style rootkit, a userland RAT, stealth mechanisms, and persistence engineered to survive reboots.

#memoryforensics #volatility3 #linux #rootkit #dfir #malwareanalysis

Summary

The challenge provided only memory artifacts, which immediately shaped my investigative strategy. Rather than searching disks for malware, I had to reconstruct attacker activity purely from memory structures, kernel objects, recovered files, process artifacts, and binary analysis.

My investigation ultimately revealed a two-component intrusion: a kernel-space rootkit masquerading as netcore.ko and a userland remote access trojan named dc_core. Together they provided stealth, command execution, privilege escalation, persistence, and anti-forensic capabilities. The interesting part was not simply identifying the malware family it was understanding how each component complemented the other.

How I Approached the Investigation

The first question I asked myself was simple: can I trust the memory image enough to start drawing conclusions? After validating the supplied hashes, I moved directly into Volatility 3 analysis.

The banner output showed that the target was a CentOS Stream 9 system. Because Linux memory analysis with Volatility 3 depends heavily on accurate kernel symbols, I spent time generating a compatible ISF file instead of rushing into plugin execution. That decision paid off later because it allowed reliable parsing of kernel structures and modules. 

vol.py -f mem.vmem linux.banners.Banners
vol.py -f mem.vmem linux.lsmod
vol.py -f mem.vmem linux.psscan

One lesson I have learned repeatedly in memory investigations is that anomalies rarely introduce themselves loudly. Instead, they appear as small inconsistencies across independent data sources. In this case, that inconsistency was an unsigned out-of-tree kernel module named netcore.

The Pivot Moment

The investigation changed direction the moment I saw the same module appearing across multiple Volatility plugins. A suspicious kernel module can be noise. The same module appearing in module listings, process relationships, and memory-resident file structures is usually a signal.

I pivoted from host triage to malware-centric analysis. Using page cache artifacts, I recovered both the kernel module and its associated userland binary. Rather than relying exclusively on static indicators, I treated them as evidence sources that could explain everything else I was seeing in memory.

Uncovering the Rootkit

Analysis of netcore.ko showed behavior strongly aligned with the Diamorphine rootkit family. What interested me most was its operational design.

  • System call hooking of getdents/getdents64.
  • Process hiding through manipulated task structures.
  • Privilege escalation through specially crafted signals.
  • Module self-concealment to evade administrator inspection.
  • Kernel-level file hiding capabilities.

Instead of creating a custom command channel, the actor repurposed the kill() syscall. That design choice is elegant from an attacker perspective because it blends malicious control traffic into legitimate operating system behavior.

The Userland Companion

The deeper I went, the more it became clear that the rootkit was only half of the story. The recovered dc_core binary functioned as a remote access trojan that handled command-and-control operations.

What stood out was the separation of responsibilities. The rootkit focused on stealth and concealment. The RAT focused on persistence, communication, and execution. Individually they were useful. Together they formed a resilient intrusion platform.

  • Encrypted configuration storage.
  • Periodic beaconing to a remote controller.
  • Remote command execution.
  • Privilege escalation attempts.
  • Persistence installation routines.

Persistence Was the Real Objective

When I examined the persistence routines, I realized the attacker was planning for failure. Instead of relying on a single startup mechanism, they layered multiple independent recovery paths.

  • Systemd service installation.
  • Root cron entries.
  • UDEV-triggered execution.

This redundancy tells us something important about the operator. The goal was not a quick smash-and-grab compromise. The goal was long-term access.

A Second Layer of Stealth

One of the more interesting findings was a trojanized shared library loaded through /etc/ld.so.preload. The rootkit already hid files at the kernel level, yet the actor added userland hiding through hooked directory enumeration functions.

That choice reflects a mindset I often look for during investigations: defense in depth, but from the attacker's perspective. If one hiding mechanism fails, another continues protecting the malware ecosystem.

Kernel-level hiding filtered specific entries before user tools could see them. Userland hooks filtered directory listings even when analysts interacted with the filesystem normally. Together they dramatically reduced visibility.

What Made This Challenge Interesting

Many memory challenges focus on artifact recovery. This one rewarded correlation. No single artifact completely explained the intrusion. The kernel module explained concealment. The RAT explained communications. The preload hook explained visibility gaps. The persistence mechanisms explained reboot survival.

The challenge was solved by continuously asking a simple question: if this artifact exists, what behavior does it explain elsewhere in memory?

Lessons Learned

  • Unsigned kernel modules deserve immediate scrutiny.
  • Memory-only investigations can reveal persistence mechanisms without disk access.
  • Rootkits rarely operate alone; supporting components often provide the real operational capability.
  • Cross-validating evidence across processes, modules, logs, and binaries dramatically reduces false assumptions.

Final Thoughts

What I enjoyed most about this challenge was the progression from uncertainty to clarity. At the beginning, all I had was a memory image and a report of anomalous communications. By the end, I could reconstruct not only what malware was present, but also how the operator thought: conceal first, persist aggressively, and maintain multiple fallback mechanisms.

That mindset became visible because memory preserves relationships. Processes reveal modules. Modules reveal binaries. Binaries reveal intent. The real investigation was connecting those layers together until the attacker's operational design became impossible to ignore.
