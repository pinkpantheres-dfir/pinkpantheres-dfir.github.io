Android FBE EXT4 and Masterkey Recovery Fix

DFIR · Android Forensics · Memory Analysis

Abstract

Android forensics has rapidly evolved in DFIR, especially with the introduction of File-Based Encryption (FBE). While FBE improves security, it significantly complicates forensic recovery. Existing tools for breaking FDE became ineffective once FBE became standard.

A research team led by Dr. Tobias Gross developed a tool capable of recovering master keys from RAM during cold-boot attacks. However, a segmentation fault in the extended Sleuth Kit rendered the tool ineffective. This research identifies and fixes that issue, restoring the tool’s functionality.

Introduction

Android is a Linux-based mobile operating system that has evolved significantly since its initial release in 2008. Early versions had limited security, but modern Android includes sandboxing, ASLR, and SELinux enforcement.

Android introduced Full Disk Encryption (FDE) in Android 5.0 and later transitioned to File-Based Encryption (FBE), which allows per-file encryption rather than encrypting entire partitions.

FBE vs FDE

  • FDE: Encrypts entire partition with one master key
  • FBE: Encrypts individual files with separate keys

FBE divides data into:

  • Device Encrypted (pre-auth data)
  • Credential Encrypted (post-auth data)

Cold Boot Attack on Android

Cold boot attacks exploit DRAM remanence — memory retains data briefly after power loss. Attackers can:

  • Cool RAM to preserve memory
  • Reboot using forensic bootloaders
  • Extract raw memory images

These techniques allow recovery of encryption keys held in RAM.

Key Recovery Method

Master keys are located using aeskeyfind, which detects AES key schedules in memory.

Decryption relies on EXT4 extended attributes:

  • Key Descriptor
  • File Nonce
  • Encryption Algorithm

The Key Derivation Function (KDF):

DEK = AES-ECB(master_key, nonce)

Problem: Tool Failure

The extended Sleuth Kit tool failed with a segmentation fault when processing real device disk images. 

fls → segmentation fault → tool breaks

This prevented:

  • Filesystem traversal
  • Key extraction
  • Decryption

Root Cause Analysis

Using gdb, the crash was traced to: 

fs_name.c → tsk_fs_name_print()

The issue occurred here: 

if (fs_file->meta->enc_attr_ptr != NULL)

Root cause:

  • fs_file->meta == NULL
  • Null pointer dereference → segmentation fault

These NULL entries originated from unallocated EXT4 inodes.

Fix Implemented

The issue was fixed by adding a null check: 

if (fs_file->meta == NULL) {
    tsk_print_sanitized(hFile, fs_file->name->name);
    return;
}

This prevents dereferencing invalid pointers.

Additional Fix (fbekeyfind)

Another issue existed in the key extraction pipeline:

  • Dependency on fls output
  • Failure in inode filtering

Regex filtering logic was improved, allowing successful key recovery.

EXT4 Analysis Insight

Manual analysis identified:

  • Invalid inodes (inode = 0)
  • Broken directory entries
  • Unallocated filesystem structures

A custom EXT4 parser was built to:

  • Parse superblocks
  • Analyze inode tables
  • Handle extended attributes

Successful Decryption

After fixing:

  • Master keys were recovered
  • KDF derived DEK successfully
  • Files decrypted correctly
