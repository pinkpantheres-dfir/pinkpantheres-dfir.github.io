Operation Red Penguin: Following an Attacker from RCE to Lateral Movement

A development server. An unexpected root password change. What initially looked like a simple credential incident turned into a full intrusion investigation involving remote code execution, privilege escalation, credential manipulation, persistence implants, and internal network pivoting.

#dfir #incidentresponse #linux #bpfdoor #rce #forensics

Summary

The investigation started with a single question: why had the root password changed on a CentOS 9 development server without authorization?

As I worked through the disk images and server logs, a much larger story emerged. An attacker exploited a vulnerable administrative web page to gain remote command execution, leveraged CVE‑2025‑32463 to obtain root privileges, deployed multiple post-exploitation tools, reset account credentials, installed a BPFDoor-based persistence mechanism, and ultimately used the compromised server as a launch point to access additional systems inside the environment.

Initial Triage

The evidence consisted of three images: root.dd, lvm1.dd, and lvm2.dd. Before looking for malware, I wanted to understand where the most useful evidence would reside.

The root filesystem provided operating system artifacts and attacker tooling, while the logical volumes contained application data and historical logs. That immediately pushed the investigation toward log analysis because attacker actions tend to leave a timeline long before malware analysis begins.

The First Breadcrumb

The first artifact that caught my attention was not a malicious binary. It was a web application.

While reviewing server logs, I noticed repeated command execution activity associated with an administrative testing page named admintest.php. The page accepted user input and passed it directly into shell execution routines without meaningful authorization controls. 

?code=<command>&execute=1

That single design flaw effectively transformed the application into a remotely accessible command execution interface.

At this point I wasn't hunting malware. I was trying to identify the first mistake that allowed the attacker onto the system. The vulnerable admin page turned out to be that mistake.

Reconstructing Initial Access

The access logs provided a nearly perfect reconstruction of the attacker's early activity.

09:49:57

10:01–10:03

The source IP associated with these actions was 13.49.23.224. The progression from reconnaissance commands to payload delivery strongly suggested a structured intrusion workflow rather than opportunistic experimentation.

Privilege Escalation Through NSS Abuse

Once I understood how the attacker landed on the host, the next question became: how did they become root?

The answer was hidden inside exa.sh. Rather than exploiting a local kernel vulnerability directly, the script abused CVE‑2025‑32463 by creating an attacker-controlled NSS environment.

The technique relied on supplying a malicious nsswitch.conf and a weaponized shared object named woot1337.so.2. When a privileged process loaded the attacker-controlled NSS module, arbitrary code executed inside a root context.

From there, the malicious library immediately escalated privileges and opened a reverse shell back to the attacker.

"The attacker didn't break into root. They convinced root to load their code."

The Password Change Mystery

The challenge description revolved around an unauthorized password change. By this stage of the investigation I already knew the attacker possessed root privileges, but I still needed to determine exactly what password had been set.

Analysis of the second-stage script p.sh revealed the answer.

The script iterated through local accounts and forcefully reset credentials for users relying on common interactive shells. Correlating execution artifacts with entries in the secure logs placed the activity shortly after privilege escalation. 

sksmsWkddlek

Password hash validation confirmed that this value had indeed been applied to affected accounts.

Building the Attacker Toolkit Inventory

exa.sh

The privilege escalation launcher responsible for staging NSS abuse and initiating root-level code execution.

woot1337.so.2

A malicious NSS module loaded inside privileged processes to execute attacker code as root.

p.sh

A credential manipulation script designed to reset user passwords to a known value.

bft

An SSH brute-force utility used during post-compromise operations.

A Linux keylogger capable of capturing user keystrokes from input devices.

tmp

A reconnaissance and vulnerability-scanning utility used to enumerate internal systems and identify opportunities for expansion.

ka

A BPFDoor-based implant designed to provide stealthy persistence and remote access.

Reverse Engineering BPFDoor

The BPFDoor implant became one of the most interesting components in the investigation.

Unlike traditional backdoors that expose listening ports, BPFDoor leverages Berkeley Packet Filters to remain largely invisible until a specially crafted packet arrives.

To understand how operators communicated with it, I moved into reverse engineering. During analysis, unique strings and authentication routines closely matched publicly available BPFDoor implementations.

Following the authentication flow eventually revealed the activation secret. 

fridaythe13th

Any packet containing the correct magic value could trigger the implant and activate its payload routines.

Following the Pivot

The compromise did not stop at the original server.

Evidence from attacker logs, password lists, IP inventories, and execution records showed that the compromised host had been transformed into an operational pivot point.

The attacker first scanned internal address space, then launched SSH brute-force activity against discovered systems before attempting interactive access.

  • 172.31.20.201 – SSH and FTP access observed.
  • 172.31.31.97 – SSH access observed.
  • 172.31.23.18 – SSH and FTP access observed.
  • 172.31.27.197 – SSH access observed.
  • 172.31.24.114 – FTP followed by SSH access observed.

What I found particularly interesting was that the attacker left behind enough tooling, logs, and execution history that the entire lateral movement process could be reconstructed long after the fact.

Full Attack Narrative

Reconnaissance

System and network information gathered through shell commands.

Weaponization

Privilege escalation and password-reset tooling downloaded into /tmp.

Privilege Escalation

Credential Manipulation

Persistence

Lateral Movement

Internal scanning, credential attacks, and SSH-based pivoting performed.

Lessons Learned

  • Administrative testing interfaces should never be exposed without strict controls.
  • Temporary directories remain common attacker staging locations.
  • NSS abuse is powerful because it executes inside trusted privileged processes.
  • Password changes are often symptoms rather than root causes.
  • Persistence mechanisms frequently reveal long-term attacker objectives.

Final Thoughts

The investigation began as a question about a changed root password. By the end, the password itself had become one of the least interesting findings.

What mattered was the chain of decisions that led to it: an exposed administrative endpoint, a privilege-escalation technique built around NSS abuse, a collection of post-exploitation utilities, a stealthy BPFDoor implant, and a campaign that expanded beyond the original host.

For me, the most rewarding part of this case was not identifying a single artifact. It was connecting individual pieces of evidence into a coherent operational story. Once those connections became visible, the attacker's entire workflow unfolded naturally.
