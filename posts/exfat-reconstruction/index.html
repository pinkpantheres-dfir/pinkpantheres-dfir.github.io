151 — Careless
Drug Dealer

He renamed a text file to a PNG and thought that was enough. It wasn't. The content was hidden — barely. But the filesystem had been quietly writing down everywhere he'd been, one timezone byte at a time. He was careless. The exFAT directory entry wasn't.

The Setup

The scenario: Suspect A has been arrested coming back from an international trip. Police believe he's been selling drugs across cities — two cities specifically, though they don't know which ones. They've got his USB. And they need something specific from it: not just timestamps, but the local timestamps — meaning they need to know what timezone the files were in when they were created and modified. That's how they'll figure out the cities.

// Evidence

File: USB.zip  |  MD5: 9e6463aa60b403697222b1442df54a68

I verified the hash first — always. A mismatched hash before you've even started means you're working on corrupted or tampered evidence. Once that checked out, I unzipped it and loaded USB.dd into Autopsy.

Three questions to answer: find the ledger, identify the timezones, then reconstruct the exact local timestamps in UTC. Simple on paper. The third one is where it gets deep.

Finding the Ledger

My first instinct with any USB image: sort files by extension in Autopsy and immediately start looking for things that don't belong. Not by filename — names lie. By what the file actually is. People who want to hide things almost always reach for the simplest trick: rename the file. Change the extension. They think that's enough.

The USB had a folder full of PNGs. Landscape photos, wildlife documentaries, the kind of thing someone would have if they wanted to look like a casual tourist. Most of them? Perfectly normal. But one entry in the file listing immediately broke the pattern:

// what caught my eye

Every other file had timestamps clustered around the same window — Modified Time around 10:21 to 10:28 on 2024-06-30. Makes sense if someone just dumped a bunch of files onto a USB in one sitting. But wildlife documentaries.png had a Modified Time of 15:40:12 on 2024-07-03. Three days later. A completely different date. That kind of temporal outlier — before I even open the file — is already telling a story. Something happened to this file separately from everything else.

I ran file on it anyway, just to confirm what I already suspected:

file "wildlife documentaries.png"
wildlife documentaries.png: ASCII text, with CRLF line terminators

Not a PNG. Not even close. Plain ASCII text with Windows line endings. The kind of file you'd create in Notepad.

Opening it — it was a structured drug sales ledger. Eight transactions, fully detailed. Supplier names, buyer names, product types (cocaine, heroin, MDMA, ketamine, meth, LSD), quantities, prices, payment methods, delivery methods, witnesses, and notes. Whoever wrote this was meticulous about record-keeping. Ironic, given what it cost them.

The effort to hide it was minimal. Rename it, put it in a folder with photos, done. No encryption, no steganography, nothing sophisticated. Just a wrong file extension. That was the "careless" in the challenge title — and honestly, in real cases, it's more common than you'd think.

The Timezone Rabbit Hole

This is the question that made the challenge genuinely interesting. It doesn't just ask for timestamps — it asks for timezone values. That's a very specific ask, and it told me exactly where to look.

When most people think about file timestamps, they think about what their forensics tool shows them. Autopsy will display a nicely formatted date and time. But that's already interpreted. To get timezone values, you need to go under the hood and look at the raw directory entry in hex — because that's where the filesystem actually stores the offset.

A quick word on why exFAT is different

FAT32 — the filesystem most USB drives used to use — stores timestamps in local time with zero timezone context. There's simply no field for it. You get a date and time, but you have no idea what timezone it was in. For investigators, this is a nightmare in cross-border cases.

exFAT fixed this. It introduced UTC offset bytes in the directory entry — one byte each for Created, Modified, and Accessed time. Each byte encodes a signed offset from UTC in 15-minute increments. So if you know how to read them, the filesystem tells you not just when but where — or at least, in what timezone.

The moment I saw the challenge was asking for timezone values specifically, I knew this was going to be an exFAT hex-level problem. Autopsy's parsed view wouldn't be enough.

Hunting the entry in hex

I went to Autopsy's hex view and started hunting through deleted directory entries — entries marked with type code 0x05, which means the file has been deleted but the directory entry is still there in the raw data. That's where the ledger file was. It had been deleted, but exFAT doesn't wipe the entry immediately — it just marks it. The bytes are still there if you go looking.

Once I located the entry for wildlife documentaries.png, I mapped out the relevant fields:

OffsetValueField
0x18–0x1BF9 53 DE 58Created timestamp (MS-DOS 32-bit)
0x1C–0x1F06 7D E3 58Last Modified timestamp (MS-DOS 32-bit)
0x20–0x2395 61 DB 4CLast Accessed timestamp
0x58D8CR Time Zone Code ← this is what we want
0x5992Mod Time Zone Code ← and this
0x5A92Acc Time Zone Code

Two bytes. 0xD8 for creation, 0x92 for last modified. Now I needed to map those to actual UTC offsets using the exFAT timezone table:

UTC-10 and UTC+4:30. I sat with those for a second. UTC-10 is Hawaii — or technically any UTC-10 territory, but Hawaii is the obvious one. UTC+4:30 is Afghanistan. Kabul. So the ledger was created somewhere in the Pacific and then opened and modified in Afghanistan. The filesystem just drew me a route. Two cities the police couldn't identify from interviews — and they were sitting right there in two bytes of the directory entry that the suspect probably didn't even know existed.

Turning Hex Into a Travel Route

The last question asks for the actual local timestamps in UTC format. This is where the previous two questions pay off — you can't do this without knowing the timezone offsets first.

Autopsy parsed the MS-DOS timestamp fields from the directory entry and showed me the local times directly:

  • Creation time (local, UTC-10): 2024-06-30 10:31:50
  • Modification time (local, UTC+4:30): 2024-07-03 15:40:12

These are the times as the device experienced them — the clock on the machine in that timezone. To convert to UTC you just apply the offset in reverse:

Creation → UTC

Local time (UTC-10):  2024-06-30 10:31:50
Add 10 hours:         2024-06-30 20:31:50 UTC

Modification → UTC

Local time (UTC+4:30): 2024-07-03 15:40:12
Subtract 4h 30m:       2024-07-03 11:10:12
→ UTC:                 2024-07-03 20:10 (minute precision as required)
// note on precision

MS-DOS timestamps in exFAT have 2-second granularity in the main field, with a separate centisecond offset field for finer resolution. The question format asked for YYYY-MM-DD HH:MM — minute precision — so that's what we report. The seconds are there in the raw data if you need them.

// Q3 Answer

Creation time (UTC+00:00): 2024-06-30 20:31:50
Modification time (UTC+00:00): 2024-07-03 20:10

And now the picture is complete. The ledger was created on June 30th in a UTC-10 timezone — almost certainly Hawaii — and modified three days later on July 3rd in UTC+4:30, which puts it in Afghanistan. That's the travel route. That's what the police needed for the joint investigation.

  • 2024-06-30 10:31 local → 20:31 UTC (UTC-10)
    Ledger created — City 1, UTC-10 region
    File disguised as a PNG. First set of transactions recorded — NYC delivery, Central Station locker drop, bitcoin payments.
  • 2024-07-03 15:40 local → 11:10 UTC (UTC+4:30)
    Ledger modified — City 2, UTC+4:30 region
    New transactions added. Same file, still sitting on the USB with the wrong extension. Still trusted to stay hidden.
  • After 2024-07-03
    Suspect A arrested on return
    USB seized. The timezone bytes he never thought about became the most important two bytes in the investigation.

What This Challenge Taught Me

On the surface this challenge looks simple — find a file, read some timestamps. But the reason I think it's a genuinely well-designed forensics problem is because it forces you to understand why exFAT stores what it stores, not just how to read it.

Most people doing USB forensics never go past what Autopsy's parsed view shows them. And in 90% of cases that's fine. But the moment you're dealing with international jurisdiction questions — where was this device, when, in what timezone — you need to know that FAT32 is blind and exFAT isn't. You need to know that those two bytes at offset 0x58 and 0x59 exist, what they mean, and how to find them when the file has been deleted.

The suspect renamed a file. He didn't understand how filesystems work. That asymmetry — his blind spot versus my understanding — is exactly what makes digital forensics interesting to me. You don't need to make mistakes to get caught. You just need to not know what the filesystem is remembering about you.

// takeaway

On exFAT volumes, always inspect bytes 0x58–0x5A of the File Entry directory structure — even on deleted entries. The CR/Mod/Acc timezone codes survive deletion and can place a device in a specific geographic region without any other corroborating evidence. FAT32 gives you nothing here. exFAT gives you everything.
