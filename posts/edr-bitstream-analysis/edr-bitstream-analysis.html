Reading the Black Box They Didn't Know Was There

A vehicle's Event Data Recorder silently captures 5 seconds of sensor telemetry before every crash. This challenge wasn't about extracting data from the EDR it was about reverse-engineering how a modern embedded ECU writes that same data, buried inside raw UDS protocol binary files, without a vendor tool in sight.

Summary

Modern vehicles contain two types of crash recorders: the traditional standalone EDR and the main embedded ECU, which now writes the same telemetry data independently. This challenge required me to parse raw .bin files generated by the ECU, map them to the UDS (Unified Diagnostic Services) protocol's Data Identifiers, and extract vehicle speed, accelerator pedal pressure, and RPM across an 11-point pre-crash timeline.

The challenge gives you a sample EDR report in PDF form as a reference key human-readable data you can cross-reference against the raw hex to build your decoding logic. Once I had that mapping confirmed, applying it to the problem binary was straightforward. The answers: at −3.0 seconds, speed was 85 kph and pedal pressure was 98%. At −5.0 seconds, RPM was 4200.

Step 2 — Understanding What an EDR Actually Records

Before touching a single byte, I read through the sample EDR report to understand the data model. A few key facts that shaped everything that followed:

  • The EDR records data only when triggered airbag deployment or impact sensor threshold. Nothing is written during normal driving.
  • Once triggered, it captures a fixed window: the 5 seconds immediately before the event, sampled at 0.5-second intervals, giving 11 data points ending at t = 0.0.
  • The values stored include vehicle speed (kph), accelerator pedal pressure (%), and rear motor speed (rpm).
  • Modern ECUs distinct from the traditional standalone EDR hardware — also write this same dataset independently. The problem binary files come from that ECU, not a traditional EDR unit.
Context

This distinction matters forensically. Traditional EDR data is extracted with a dedicated cable and proprietary software (like Bosch CDR). ECU-sourced EDR data lives in the main embedded system's memory and requires understanding the communication protocol the ECU uses to expose it which is UDS.

Step 3 — Discovering the UDS Protocol Link

I knew what the data contained. I didn't yet know how the ECU structured it on disk. That required understanding how ECUs communicate diagnostic data — which led me into research on automotive diagnostic protocols.

The Unified Diagnostic Services (UDS) protocol defined in ISO 14229 is the standard by which diagnostic tools interrogate vehicle ECUs. It operates over the CAN bus and uses 16-bit Data Identifiers (DIDs) to address specific data records. The protocol can read both static data (VIN, serial number) and dynamic data (live sensor values). Crucially, it can also read stored event data which is exactly what these .bin files represent.

  • EDR Reference ReportsCrashDataGroup - Tesla EDR Documents - Real-world EDR reports that confirmed the data layout used in this challenge.
  • Diagnostic Protocol OverviewSirinSoftware - Modern Car Electronic Diagnosis Protocols - Introduced me to the UDS protocol and its role in ECU communication.
  • DID ReferencePiEmbSysTech - DID of UDS Protocol - Critical resource mapping DID ranges to their data types.

Step 4 — Mapping Data Identifiers to the Binary Files

The UDS protocol's DID space is divided into standardised ranges. The ones relevant to this challenge:

DID (hex)NameContent
0xF190VIN Data Identifier17-character Vehicle Identification Number, stored as ASCII hex
0xFD00–0xFEFFSystem Supplier SpecificManufacturer-defined records includes sensor data, event logs, operational counters
0xFD91Speed / Pedal / RPMContains the pre-event vehicle speed, accelerator pedal percentage, and rear motor RPM the key record for this challenge

The file naming directly reflects the DID fd91.bin maps to DID 0xFD91. Once I understood this, navigating the binary dump became a matter of matching offsets to known data fields.

Step 5 - Confirming the Encoding on the Sample

Before parsing the problem file, I validated my decoding approach against the sample report which gives me known ground truth values I can compare against.

First, I tested whether string data was ASCII-encoded by checking the VIN. The sample report's VIN is 7KJSA1H50EFP00000. Pulling the F190 hex bytes and running them through an ASCII converter: 

def hex2ascii(k):
    for i in k:
        print(chr(int('0x'+i, 16)), end="")

hex2ascii("35 59 4A 53 41 31 48 32 31 45 46 50 30 30 30 30 30".split())
# → 5YJSA1H21EFP00000

That's a different VIN than the sample report listed but when I cross-referenced this against other Tesla EDR documents I found online, 5YJSA1H21EFP00000 matched a real vehicle in those external reports. The VIN in the challenge sample report (7KJSA1H50EFP00000) appears to be a placeholder. What matters is confirmed: string data is stored directly as ASCII hex.

Next, I converted the known speed values from the sample report's Event Data table into hex to locate them in the FD91 binary: 

def dec2hex(k):
    for i in k:
        print(hex(i)[2:].zfill(2), end=" ")

# Sample report speed column: 69, 66, 61, 58, 56, 55, 54, 57, 51, 46, 45
dec2hex([69, 66, 61, 58, 56, 55, 54, 57, 51, 46, 45])
# → 45 42 3d 3a 38 37 36 39 33 2e 2d

Searching for that hex sequence inside the sample FD91 binary it appeared at the very start of the data block at offset 0x0000. The layout was confirmed: speed values are stored sequentially as single bytes in decimal-direct hex (each byte value is the speed in kph), starting at the beginning of the block.

FD91 - Sample vehicle (offset 0x0000)
0000  45 42 3D 3A 38 37 36 39 33 2E 2D 00 00 00 00 00  ← speed values (kph, hex-direct)
0010  04 0C 23 57 62 63 33 31 2D 2B 2A 29 28 29 28 25 23  ← rpm values
0028  00 00 00 00 00 04 0C 23 57 62 63 00 00 00 00  ← pedal pressure (%)
Encoding Gotcha

At first glance you might assume the hex is ASCII-encoded like the VIN. It isn't numeric sensor values are stored as raw binary integers, not as ASCII character representations. The byte 0x45 means 69 (decimal), not the character "E". Running hex2ascii on sensor data gives garbage. The correct conversion is int('0x45', 16) = 69 direct base-16 to decimal.

Extracting the three sequences speed, pedal pressure, RPM and converting each from hex to decimal: 

def hex2dec(k):
    for i in k:
        print(int('0x'+i, 16), end=" ")

speed      = "39 45 4a 51 55 5a 61 65 6b 71 7b"
pedal_pres = "23 56 58 60 62 62 62 62 62 62 63"
rpm        = "2a 2d 2d 30 37 37 39 3a 3b 3c 3c"

hex2dec(speed.split())
# → 57 69 74 81 85 90 97 101 107 113 123

hex2dec(pedal_pres.split())
# → 35 86 88 96 98 98 98 98 98 98 99

hex2dec(rpm.split())
# → 42 45 45 48 55 55 57 58 59 60 60

What the Timeline Actually Shows

Looking at the reconstructed data as a narrative rather than a table, the story of the final 5 seconds is clear and unambiguous. At t = −5.0s the vehicle is doing 57 kph with only 35% pedal input — the driver is pressing moderately, possibly in a normal driving condition. Then, at t = −4.5s, something changes: pedal input jumps to 86% and speed begins climbing rapidly.

From t = −3.5s onward, pedal pressure stabilises at 96–98% — essentially full throttle. The vehicle accelerates from 81 kph at −3.5s to 123 kph at the moment of impact. That's a 42 kph increase in 3.5 seconds under near-maximum acceleration. The RPM climbs correspondingly from 4800 to 6000, confirming the motor is being pushed to its upper range.

Forensic Reading

This is the signature of an unmitigated acceleration event. No braking input appears anywhere in the pedal pressure column. The driver did not attempt to slow down before impact. Whether that reflects panic, incapacitation, or intent would require additional evidence — but the EDR data itself is unambiguous about what the vehicle was doing.

Forensic Takeaways

  • UDS DID 0xFD91 is the pre-event sensor record. In the System Supplier Specific range (0xFD00–0xFEFF), DID 0xFD91 stores the 11-point pre-event timeline for speed, pedal, and RPM. The binary file naming convention directly encodes the DID fd91.bin is not arbitrary. Once you know this mapping, navigating ECU dump archives becomes systematic.
  • Numeric sensor values are raw hex-to-decimal, not ASCII. String data (VIN, identifiers) is ASCII hex. Sensor readings are single-byte integers in base 16. Applying the wrong decoding to sensor data produces plausible-looking but completely wrong numbers. Always validate against a known reference before treating parsed values as evidence.
  • The sample report is the Rosetta Stone. Providing a sample PDF with human-readable values alongside raw binary dumps is effectively giving you a key. The workflow is: take a known value from the report, convert it to hex, find it in the binary, and confirm the offset. Once the offset layout is mapped, the problem binary parses cleanly with identical code.
  • Modern ECUs are independent crash recorders. The traditional EDR — the dedicated hardware unit — requires specialist extraction tools. The ECU's copy of the same data is accessible via the UDS protocol over any standard diagnostic interface. In cases where the physical EDR is damaged or inaccessible, the ECU binary may be the only surviving copy of pre-crash sensor telemetry.
  • CAN bus forensics is an expanding discipline. As vehicles become more software-defined, the forensic surface grows. EDR data is just one slice the same UDS protocol exposes fault codes, odometer records, and calibration histories. An examiner who understands DID addressing can extract and interpret a significantly wider evidentiary picture than one limited to traditional EDR extraction workflows.

Conclusion

The challenge title asks "how is EDR data written?" and the answer, once you work through the protocol stack, is surprisingly transparent. The ECU writes UDS-compliant binary records, addressed by standardised Data Identifiers, encoding sensor values as direct hex integers in a sequential fixed-width format. There is no encryption, no obfuscation. The only barrier is knowing which DID to look in and how the bytes are encoded.

Once that knowledge is in place built here by cross-referencing the sample report against the binary, then validated against external Tesla EDR documents reading the problem vehicle's pre-crash telemetry was a matter of three one-liner Python functions and a hex table lookup.
